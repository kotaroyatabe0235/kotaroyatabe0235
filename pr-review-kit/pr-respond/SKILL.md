# pr-respond

PRについた **レビューコメントに対応する** スキル。
コメントを読む → 直す → 返信する → スレッドを解決する、までを扱う。

## 前提

- `gh` コマンドでログイン済みであること。
- 返信は **日本語** で書く。
- **push と 返信の投稿の前に、必ずユーザーに見せて確認をとる。** これはユーザーとの合意事項。
- 指摘が間違っていると思ったら、黙って直さない。反論も立派な対応。

## 場所

スクリプトは `~/workspaces/kotaroyatabe0235/pr-review-kit/scripts/` にある。

## 手順

### 1. 未解決のコメントを取り出す

```bash
cd ~/workspaces/kotaroyatabe0235/pr-review-kit/scripts
python3 fetch_threads.py <PR番号>
```

インラインのレビューコメント（スレッド）が、未解決のものだけ出る。
各スレッドに `thread_id`（解決に使う）と `reply_to_id`（返信に使う）が付いている。

PR全体への普通のコメント（インラインでないもの）は別で見る:

```bash
gh pr view <PR番号> --comments
```

解決済みも含めて全部見たいときは `--all`、機械で処理したいときは `--json` を付ける。

### 2. 作業ブランチに移る

そのPRのブランチにいないと直せない。

```bash
gh pr checkout <PR番号>
git pull
```

`git status` がきれいなことを確かめる。他人の変更を巻きこまない。

### 3. コメントを1つずつ仕分けする

読んだら、次のどれかに分類する。**ここでユーザーに一覧を見せる。**

- **直す** — 指摘のとおり。どう直すかを1行で書く。
- **直すが別のやり方で** — 指摘の意図には同意するが、直し方は変える。理由を書く。
- **直さない** — 意図があってそうしている / 指摘が事実と違う / このPRの範囲外。理由を書く。
- **質問に答えるだけ** — `[ask]` などコード変更が要らないもの。
- **別Issueにする** — 大きすぎてこのPRでは無理なもの。

`outdated` と出ているスレッドは、そのあとコードが変わっている。
今のコードを読み直して、まだ問題が残っているか確かめてから仕分ける。

### 4. 直す

- **1コメント＝1コミット** にする。あとで「どの指摘に対応したか」を追える。
- コミットメッセージにはコメントの要点を書く。例: `Fix crash when items is empty (review comment)`
- 指摘された箇所だけ直す。ついでのリファクタリングを混ぜない。
- 直したらテスト・型チェック・lint を走らせる。プロジェクトのCLAUDE.mdにコマンドが書いてあれば従う。

### 5. push する（確認してから）

変更の一覧（`git log --oneline` と `git diff` の要約）をユーザーに見せて、
「pushしていいですか」と聞く。**返事を待つ。**

```bash
git push
```

### 6. 返信する（確認してから）

返信文は、コミットのSHAを添えると相手が追いやすい。

返信文の型:

- 直したとき: `直しました。<何をどう直したか1〜2行>（<コミットSHA先頭7桁>）`
- 別のやり方にしたとき: `<指摘への同意>。ただし<理由>なので、<やり方>にしました（<SHA>）`
- 直さないとき: `<理由>のため、このままにします。<補足>`
- 質問への回答: そのまま答える。

返信文を全部ユーザーに見せて、確認をとってから投稿する:

```bash
gh api --method POST \
  "repos/<owner>/<repo>/pulls/<PR番号>/comments/<reply_to_id>/replies" \
  -f body="返信本文"
```

`reply_to_id` は手順1の出力にある。

PR全体への普通のコメントに返すときは:

```bash
gh pr comment <PR番号> --body "返信本文"
```

### 7. スレッドを解決する

対応が済んで、相手の確認が要らないスレッドだけ解決する。
議論が続いているものや、こちらが質問を返したものは **開けたままにする**。

```bash
gh api graphql \
  -f query='mutation($id:ID!){ resolveReviewThread(input:{threadId:$id}){ thread { isResolved } } }' \
  -F id='<thread_id>'
```

### 8. まとめを報告する

最後にユーザーへ、対応した件数・直さなかったものとその理由・pushしたコミットを短く伝える。

## 注意

- **指摘に納得できないまま直さない。** 直すと「同意した」と受け取られる。
  違うと思うなら、返信で理由を書いて相手に判断してもらう。
- 自分が対応していないスレッドを解決しない。指摘を消したように見える。
- force push（`git push -f`）はしない。レビューコメントの位置がずれて、
  何を指摘されたのかわからなくなる。
- コメントが多いときも、まとめて雑に返さない。1スレッド1返信が基本。
