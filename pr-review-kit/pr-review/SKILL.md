# pr-review

GitHub の PR を読んでレビューし、指摘を **日本語のインラインコメント** として投稿するスキル。

## 前提

- `gh` コマンド（GitHub CLI）でログイン済みであること。`gh auth status` で確認できる。
- コメントは **日本語** で書く。
- **確認なしに投稿しない。** コメント案を全部ターミナルに出し、ユーザーが「OK」と言ってから投稿する。
  これはユーザーとの合意事項。
- 投稿するレビューの `event` は基本 `COMMENT` にする。`APPROVE` / `REQUEST_CHANGES` は
  ユーザーがはっきりそう頼んだときだけ。（自分のPRは GitHub 側の仕様で approve できない）

## 場所

スクリプトは `~/workspaces/kotaroyatabe0235/pr-review-kit/scripts/` にある。

## 手順

### 1. PRの中身を集める

PR番号がわからなければ、まずどのPRか確かめる（`gh pr list`）。

```bash
gh pr view <PR番号> --json number,title,body,author,headRefName,baseRefName,url,files
gh pr diff <PR番号>
```

diff が長いときは `gh pr diff <PR番号> --name-only` でファイル一覧を見てから、
気になるファイルの diff を絞って読む。

### 2. まわりのコードも読む

diff だけを見て指摘すると外しやすい。変更された関数の呼び出し元、
似た処理をしている既存ファイル、テストの有無は必ず確認する。
「この変更で壊れるのは具体的にどの入力のときか」を言えないものは、指摘に含めない。

### 3. レビューの観点

上から順に大事。下の方だけを大量に挙げるレビューにはしない。

1. **バグ・こわれ方** — nullやundefinedの取りこぼし、境界値（0件・1件・最大件数）、
   非同期の待ち忘れ、例外を握りつぶしている箇所、既存の呼び出し元が壊れる変更。
2. **セキュリティ** — 入力のバリデーション不足、秘密情報のコミット、権限チェックの抜け。
3. **設計・置き場所** — そのロジックがそこにあるべきか。既にある関数の作り直しになっていないか。
4. **テスト** — 新しい分岐にテストがあるか。
5. **読みやすさ** — 名前、深すぎるネスト、コメントすべき「なぜ」が書かれているか。

### 4. コメント案をJSONにまとめる

作業用ファイル（スクラッチパッド）に `review.json` を作る。

```json
{
  "body": "全体のまとめ。よかった点を1〜2行、そのあと重い指摘の要約。",
  "event": "COMMENT",
  "comments": [
    {
      "path": "src/foo.ts",
      "line": 42,
      "side": "RIGHT",
      "body": "[must] `items` が空配列のとき `items[0]` が undefined になり、次の行で落ちます。\n\n```suggestion\n  const head = items[0];\n  if (!head) return null;\n```"
    }
  ]
}
```

コメントの書き方:

- 先頭に重さのラベルを付ける。
  - `[must]` — 直してほしい（バグ・セキュリティ）
  - `[imo]` — こうした方がよいと思う（好みが混じる）
  - `[nits]` — 細かい。直さなくてもよい
  - `[ask]` — 質問。意図を知りたいだけ
- **なぜ問題か** を必ず書く。「〜が良くない」だけで終わらせない。
- 直し方がはっきりしているときは ` ```suggestion ` ブロックを使う。
  そのままGitHub上で反映できる。
- 断定できないことは `[ask]` にして質問の形にする。推測を事実のように書かない。
- 同じ指摘が5箇所にあるなら、1箇所にコメントして「他にも同様の箇所が4つあります」と書く。
  同じ文を5回貼らない。

`line` は **変更後のファイルの行番号**（`side: "RIGHT"`）。
削除された行を指したいときだけ `side: "LEFT"` と変更前の行番号を使う。
複数行にまたがる指摘は `start_line` を足す。

### 5. 行番号が正しいか検算する

GitHub は diff のハンク（変更のかたまり）の中の行にしかコメントできない。
範囲外を指定すると 422 エラーで全部投稿されない。先に確かめる:

```bash
cd ~/workspaces/kotaroyatabe0235/pr-review-kit/scripts
python3 post_review.py <PR番号> --file <review.jsonのパス> --dry-run
```

どの行ならコメントできるかを知りたいときは:

```bash
gh pr diff <PR番号> | python3 diff_lines.py
```

### 6. ユーザーに見せて確認をとる

コメント案（ファイル名・行番号・本文）をターミナルにそのまま出して、
「この内容で投稿していいですか」と聞く。**返事を待つ。**
直しの指示があれば `review.json` を直して、もう一度見せる。

### 7. 投稿する

```bash
python3 post_review.py <PR番号> --file <review.jsonのパス>
```

投稿されたレビューのURLが出る。ユーザーにそのURLを伝える。

別のリポジトリのPRなら `--repo owner/name` を付ける。

## インラインコメントが付けられないとき

diff の外（変更していないファイル、PR全体の話）を指摘したいときは、
インラインではなく普通のコメントにする。

```bash
gh pr comment <PR番号> --body-file <本文ファイル>
```

本文の中で `src/foo.ts:42` のようにファイルと行を書けば、読む人は追える。

## 注意

- コメントは投稿すると相手に通知が飛ぶ。取り消しても通知は消えない。だから確認を必ずとる。
- 同じPRに何度もレビューを投げ直さない。直す前提のときは、投稿前の段階で直しきる。
- 指摘がゼロだったときは、無理に何か探さない。「見たが指摘なし」と伝えて、
  投稿するかどうかをユーザーに決めてもらう。
